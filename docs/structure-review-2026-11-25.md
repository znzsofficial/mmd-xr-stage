# 项目维护审计：什么会让下一次改动越来越贵？

**建议先用“进 VR 失败也不丢布局”收口一次交付，再做有边界的小行星重构。** 产品目标仍是让玩家在 Quest 用自己的演员摆姿、看动作、互动。引擎选型、布景和诊断都是手段。并行适合解决一个已经选定的问题，不适合让每个调查都变成要实现、部署、写交接、请玩家复测的新项目。

基线：源码 `44caa23`、产品 `1d54f10`；另读了工作区上一轮未提交的交接草案。五路审查覆盖运行时与 UI、移动与布景、文档与计划、验证与发布、实验与停用资产。依据是源码、导入图、Git 历史、已有发布证据，以及用合成输入对拒权路径、教室放置规则的两次 Node 核对。未启动渲染器、重跑套件或采集设备数据。这是一份有日期的审计，不是另一份常驻任务表。

## 首要问题是交付单位失控

- **一次发布承担多个互不依赖的承诺。** `6db0bb7` 同时触及移动、演员形态、裙面耗时、资源释放与诊断，共 60 个文件；`1d54f10` 同批交付卫星跳跃和仅在实验页运行的双手裙摆，共 40 个文件。[发布记录](./release-history.md)区分了证据，但同一版本的归因、回退、问玩家什么仍需要人工拆解。可以批量部署；改动应能独立审阅、验证、回退，不必为拆提交而增加部署次数。
- **文档已成为发布工作，而不仅仅是其产物。** 按 Git 主线作者日期，11 月 25 日到 `44caa23` 有 31 次提交，其中 16 次只改 Markdown，20 次改交接页、12 次改发布记录、10 次改旧分块清单。不能把它们加总或等同于浪费工时；可以确认同一结论需要在多个位置反复维护。11 月 20 日审查基线 `b69584a` 到本次基线，`docs/` 的 Markdown 由 44 增至 91，根代理指南约由 14 KB 增至 30 KB。
- **不能由「文件多」推导重写。** 从 `src` 剔除测试、基准和声明，擦除 TS 类型后解析相对静态 import／re-export：602 个模块、1,802 条不同的本地有向边，未发现多模块强连通分量。此口径不含动态导入、回调和 store 订阅；恰恰是后者让“没有导入环”与“行为容易改”成为两件不同的事。`mmdVrStore`、`backpack/store` 分别被 62、55 个模块直接引用；引用多不是缺陷，多条路径都能改变同一状态才值得整理。

**把回归留给开发者。** [已提交的双眼行走脚本](../scripts/verify-home-walk-iwer.cjs#L1-L6)默认从机器临时目录取 Playwright 和 IWER；它很有价值，但干净检出不能只靠项目锁文件复跑。把所需工具版本、匿名输入、实际脚本入口和失败退出码一起固定；只先迁一条关键路线。不把个人 PMX 或原始头显记录搬进 CI，也不把缺少 GPU 写成测试通过。

**可清但不急。** 舞台 42 个非 `master` 本地分支的尖端均已合入；它们是指针，不是 42 个待办。只读核对在 `local-review/verification` 找到多份与已知兼容资源 SHA-256 相同的构建副本，保留每种内容一份的理论重复量约 1.37 GiB。如空间真有压力，先做恢复索引并演练还原，再由所有者决定。私模、独有截图与设备报告、尚未投稿的 loader 工作树、已发布固定版均不按年龄删除。本次没有退役或删除任何资产。

## 有具体反例的结构边界

**最先修的不是最长的文件：权限拒绝会提前清空多景布局。** [正式 XR 入口](../src/mmdVrShowcase/xr/requestMmdVrEnter.ts#L30-L58)在 `setEntering` 就让[背包准备空场](../src/mmdVrShowcase/backpack/store.ts#L119-L125)；[通用入口](../src/xr/requestImmersiveEnter.ts#L52-L89)在这之后才申请 session，[失败收尾](../src/mmdVrShowcase/mmdVrStore.ts#L242-L272)不恢复各景数据。**本次已做 Node 复现**：用合成 File 建立教室／泳池两景，以泳池为末景；运行实际入口、公共进入流程和 store，只为会话提供者注入拒权。返回 `failed` 后：房间布局 **2→0**，已存资产及动作绑定各 **1→0**，源文件 **2→2**，末次单景 `savedStage` 仍为泳池。没有删用户磁盘文件，也不是安全预检失败；丢的是本页之前的摆放与绑定记录。建议将“申请一次空场”与“确认替换页面旧布局”分成两步，按进入代次提交或回滚；成功空场仍按既有产品规则运行。

**同一演员操作的结果受按钮入口影响。** 背包命令在[执行成功后](../src/mmdVrShowcase/stage/StageRoom.tsx#L541-L551)按剩余动作时长修正时钟、必要时停播再提交布局；详情移除走[帧队列](../src/mmdVrShowcase/stage/roomModelCommands.ts#L13-L35)和[另一套收尾](../src/mmdVrShowcase/stage/StageRoom.tsx#L409-L426)。时长 setter 不会夹当前时间。因而在暂停 30 s 时移除 60 s 演员、仅留下 10 s 演员，两条代码路径对当前时间的处理不一致。[已有两入口测试](../src/mmdVrShowcase/stage/MmdVrStage.test.tsx#L180-L201)验证了渲染器更换不使旧人复活，却恰好移除无动作的那个人。另一个同类风险是暂停且关物理，隐藏后拖时间再显示：运行时[跳过隐藏演员](../src/mmdVrShowcase/mmdRuntime/mmdRuntime.ts#L1149-L1164)，房间[按整房时间决定跳过求值](../src/mmdVrShowcase/stage/StageRoom.tsx#L662-L674)。后两项是代码路径审查，未声称看到实机故障。共用“成员变更后的时钟／快照提交”和“重新可见后的姿态失效”即可，保留异步命令 token、过期帧保护及房间唯一帧调度者，不应先换 store 框架。

**小行星：需要重构的是交接，不是整个物理。** `24d4220`、`d685552`、`6db0bb7`、`1d54f10` 先后处理着陆、航程连续、母星及卫星跑跳。[当前马达](../src/mmdVrShowcase/movement/PlanetMotor.tsx#L110-L193)仍要在起跳、停放 Rapier、捕获和后续步行处反复组合 `free/ride/leap/orbit` 及 `captureStance`。好的一面是 XR 原点已经集中写入，普通跳与真正跨星已可区分。下一步只收敛**一个活动模式、一个接地结果、一个最终视图出口**；保持追踪侧倾、风道、跨井保护和物理参数。用现有输入与[修前／修后双眼记录](./performance/quest-2026-11-25-1149.md)校对，不要求玩家为拆代码重新作证。模拟相同不等于实戴舒适度已获确认。

**布景：类型完整的注册表并不保证各系统看见同一堵墙。** [教室后墙](../src/mmdVrShowcase/scenery/ClassroomProps.ts#L22-L27)实际门洞为 `x=-4.03±0.93`。用正式[放置规则](../src/mmdVrShowcase/scenery/placementAreas.ts#L32-L46)从 `(0,1.6,4)` 指向合法砖路 `(-4.03,0,6.45)`，在 `z=5.6` 穿墙处 `x=-2.632`，位于门洞之外。直接运行得到落点合法、`visiblePick=true`；换到正对门洞也为 `true`。[确认逻辑](../src/mmdVrShowcase/backpack/BackpackPlacement.tsx#L50-L83)正使用这两个谓词。这是规则反例，不是一次实际点击的画面。另有两块卫星平台允许放导入 GLB，而[卫星地面马达](../src/mmdVrShowcase/movement/moonWalk.ts#L16-L41)查的是壳和内建布景，不是已放置物件；这是静态发现，需开发者用挡板夹具复核。按景共用门洞／平台的布局事实即可，不应让头部碰撞、脚下支撑和放置射线使用同一判定。

**假绿比少一个测试更危险。** `bb56fe1` 移除了正式 XR 对几个房间旧二维移动器的分派；[现行接线](../src/mmdVrShowcase/movement/usePlayerMovement.ts#L73-L118)走地面马达。可是[秦淮“走上楼再回来”](../src/mmdVrShowcase/scenery/qinhuai/songhouseLayout.test.ts#L6-L18)仍用 `moveInSonghouse`；喜院也有同类用例。它们能证布局谓词，不能证明今天的玩家能走上楼。保留原坐标，把**一条**代表路线接到正式马达和对应实体上，等价覆盖后才删该旧实现或把测试改名为布局检查；不重写全部场景测试。

## 整理顺序（建议，不是开工授权）

1. **先让一次小交付不用玩家兜底。** 入口拒权丢布局是首个样本。开发者写一个含两景的失败／取消／成功对照，修权限请求的提交边界；发版负责人用现有工具收成一个可重复入口，验同一个制品再晋级。这一阶段就用现成环境，不以建完全部 CI、整理完文件树作为前提。退出：同一页面拒权可继续两景，成功开空场符合原语义，老请求不覆盖新请求；另一位维护者能复跑；**用户需要做的验证为零**。
2. **唯一主动重构：小行星模式交接。** 用当前固定版回放先保行为，再换状态表示；做完用相同输入重播，并清走已替代的判断。无新行为就不发一次“请重测”的通知。退出：模式唯一，脚位与视图提交口唯一，普通跳／受保护着陆／风道仍分得清，已有数据的路线可在维护环境运行。真实舒适度未确认就按未确认记录，不能卡住代码整理。
3. **只恢复一个产品决策。** 下一项才是现有 WebGPU 实验的真实 VMD 播放→暂停双托→撤回→续播对照。实验负责人先做可自动化的外观、回落、整帧配对和失败回退；若仍有值得推广的收益，再在候选版集中收一次设备独有的体验或时序证据。够好才接同一背包的一景一人；不够就冻结该线。没有设备证据时保持可选实验，不让玩家补一整张单。

**以后什么工作可以开始？** 一次只有一个已批准的玩家结果，配一个能否停止的判据。新反馈先归为阻断该结果、可留作证据、或下轮另议；仅数据丢失／关键路径不可用等严重回退可打断。每次只在事实所有者处更新：玩法归操作指南、实验结论归实验、发布归制品记录；交接页写“当前／下一个／暂停”，不再逐项转抄。子代理可并行采证或实现同一里程碑，主会话负责证据整合、取舍和发布。未获批准的发现留在本审计，不自动拆成新待办。

**保住什么？** 页级文件与布局、观看会话缓存、房间实例与物理世界三种寿命已经拆开；屏幕和 XR 共用房间；loader 通用修改在一个 fork，游戏锁定经过校验的制品。这些边界实际挡住过旧帧取走新房命令、换 renderer 复活已移除演员等问题，值得作为重构支点，而非推倒重来。整理是否成功，看下一次任务能否少跨一处状态、少重复一次构建、少让玩家做一次本可自动化的验证，不以删了多少文件算成绩。
