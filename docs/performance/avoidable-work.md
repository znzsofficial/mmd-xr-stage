# 不降画质，舞台还能少做什么？

调查基线：舞台 `d3e7fb8`、loader fork `c4d56e8`。以下均是设计，尚未实施。证据来自已存回放、当前源码和一次无渲染的调用计数；本轮没有新测 FPS 或毫秒数。

## 首选：WebGPU 播舞时复用未变的顶点形态

**玩家目标：**保持眼图、衣着、表情和物理精度，让人站在原机位看同一段舞时少做 GPU 工作。这项只针对可选的 WebGPU XR。

**实际链路。** [舞台](../../scripts/webgpu-actor/stageActorBackend.js)已把两眼、多人共用的材质准备合到每跟踪帧至多一次。但只要这次需要准备，[loader 仍遍历已挂接的模型](https://github.com/znzsofficial/three-mmd-loader/blob/c4d56e8/src/webgpu/pipeline.ts#L318-L337)，[写权重并提交稀疏形态计算](https://github.com/znzsofficial/three-mmd-loader/blob/c4d56e8/src/webgpu/sparse-morph-runtime.ts#L139-L161)。骨骼随舞移动，不意味着这一步蒙皮之前的顶点／UV 偏移也在变。

[已有两组不同口径的证据](./README.md#webgpu-单人播舞)：30,653 顶点的原件，在固定舞段的 240 次求值里，239 对相邻权重完全相同。若首帧算一次、没有外部写入，单是位置输出理论上可少处理 `239 × 30,653 = 7,326,067` 个顶点。另一组实际双眼回放中，1,205 帧里有 1,137 帧在权重不变时仍观察到 Three compute；后者是整组计数，并非每次都已归因给形态。

**最小设计。** 先只给舞台接入按演员实例复用；loader 原有调用默认行为保留。比较实际送往 GPU 的 Float32 权重，不按动作时刻或数组引用判断。首次、换实例／设备、目标缓冲替换或不确定时完整计算。只跳过稀疏形态提交；材质显隐、换画风、骨骼、Bullet、布料仍执行原路径。第一版位置和 UV 一起重算，不为细分通道再加一套状态。

**最容易做错的是摆姿。** [手动裙片](../../scripts/webgpu-actor/poseSkirtDisplay.js)会向同一位置缓冲 `addAssign`；连续跳过基础计算会让偏移叠加，退出时还可能残留。第一版宁可少省：修裙有效期间照旧逐次重算后再叠加；最后一次写过的演员退出修裙时强制重建一次干净输出。普通 GPU 裙摆读取[独立点位与目标](../../scripts/webgpu-actor/clothSurface.js)，不需要连它一起暂停。

**收工条件。** 固定样本的恒定段应从 240 次基础位置计算降至首帧 1 次；眨眼 0→半→全→0、独立 UV 变化、暂停抬腿→恢复原动作、两人中只改一人、收回重放均须匹配原版两眼。恢复正常电源后比较同一原件交替 A/B：记录形态专属提交次数、`threeComputeMs` 与可见回调 P95。桌面若只证实少算，就只报少算；Quest 的慢帧收益在头显单列。

## 默认 XR 也可做：没有能振动的手柄时不为触觉查接触表

[房间](../../src/mmdVrShowcase/stage/StageRoom.tsx)在物理开、未忙且触觉偏好非关时，约 30 Hz 查询两侧接触；[真正发脉冲的组件](../../src/mmdVrShowcase/xr/contact/MmdVrControllerColliders.tsx)还要求该侧握把可追踪、gamepad 有可用振动接口。纯手追时可以有手与衣物的物理接触，却没有手柄来消费这次触觉查询。现有查询按演员、按物理步缓存；同一步读左右两侧通常共用一次扫描。

**旧数据的边界：**重新读取 `local-review/heavy-bullet/paired-*.json` 与 `contact-pair.mjs`。四份实模的正式稳态段每份均为 240 次轮询、0 次手柄命中；该段手柄明确停放，后面的扫入／撤回段另有正命中。这能验证测试覆盖，不能说真实玩家有多少帧可以跳过。握着可振动的手柄、只是暂时没碰到演员，仍要查询。

**最小设计与验收。** 让房间在轮询时得到当前会话两侧是否有可消费触觉的输入；两侧都无且调试面板未要求计数时，清旧接触标志并跳过这次查询。保持 Bullet 子步、手部胶囊、道具和调试读数各自的原路径。用同一暂停裙摆测试双手追、无振动 gamepad、左右手混用、恢复手柄及切换会话：无消费者时触觉专用查询为零，手仍能托起衣摆；恢复后第一次新接触产生一次反馈，无继承的旧脉冲。单侧有消费者时不预估“节省一半”。

## 小行星摆场：演员变化不重建静止道具的行走网格

旋转或显隐演员会经 [房间命令](../../src/mmdVrShowcase/stage/roomModelCommands.ts) → `publishEdits` → `syncModelList` → [`publishLive`](../../src/mmdVrShowcase/stage/stageActors.ts)，发布新的在场名单。[星球 `LandingSolids`](../../src/mmdVrShowcase/movement/PlanetPhysics.tsx)把整个名单用作依赖，把演员圆柱和导入物件挂在同一固定刚体上。即使 GLB 没动，也会销毁旧刚体，重走可见网格，把顶点变换到世界坐标，再建三角碰撞体。这是**摆场操作**的开销，不能用来解释原地播舞每帧慢。

**本轮计数复现。** 挂载实际 `PlanetPhysics`，场景里放一个普通网格和一个有两个实例的网格，使用真实背包状态订阅，以计数接口代替 Rapier。初次建 3 个三角碰撞体；只移动演员，再建 3 个；重发内容相同的名单，又建 3 个；隐藏实例物件，剩下未变的普通网格又建 1 个。累计 **3→6→9→10**。未创建 WASM 世界、未测时。复现：`pnpm exec vitest run --config local-review/work-count-study/vitest.config.mts`。

**最小设计与验收。** 当前房间持有演员圆柱与各个物件的独立碰撞句柄，仍使用同一个行走世界。按挂载根身份和实际碰撞输入区分变化；移动、缩放、显隐或替换哪个物件，只更新那个物件；保留实例矩阵、子网格可见性、原绘制索引范围和空心结构。同一输入无法确认未变时重建该物件。降级行走使用的 [`planetPad`](../../src/mmdVrShowcase/movement/planetPad.ts)另有查询缓存，不能借用 Rapier 句柄。上述夹具在没有增加道具时累计创建目标为 **3→3→3→3**；另外必须实际走过空心门框、撞低梁、站上平台后移走它、退出并重入，验证新位置生效、旧位置无残留。

## 首次等待：先查选画风之前已经做了多少事

WebGPU 虽按需加载画风贴图，但[挂接演员](../../scripts/webgpu-actor/materialAdapter.js)时，只要材质槽可识别，默认原 MMD 也会尝试准备仿终末地用的[描边方向](../../scripts/webgpu-actor/endfieldOutline.js)；识别到皮肤槽时还会建立[薄皮遮罩](../../scripts/webgpu-actor/skinTransmission.js)。从已有 13 份原件记录中，12 份成功切过画风并还原，9 份有皮肤槽。这 9 份按原件顶点数，仅遮罩的 Float32 数组就各为 **240,236–308,760 字节**。这是数组规模，未测这部分在首次挂接的占比。

若目标改为“从背包放下更快看到人”，优先单独计这两项。若占比够大，方案是在 TSL 替换几何前保住必要的只读原始属性、分组和材质元数据，首次选仿终末地才算专用数据。不能直接把现有 `prepareOutline` 移到按钮回调：它明确拒绝替换后的几何。按实例持有，换肤替身、取消和离场时退役旧工作；核对原画风首次双眼、首次切风格的最长停顿、画风来回像素与额外持有字节。若只是把同一个大停顿移到按钮上，保留原方案。

WebGL 另走 [`prepareModelGpu`](../../src/mmdVrShowcase/stage/loading/prepareModelGpu.ts)：每上传一张纹理让出一次，代码里写了 12 ms。复读两份过去的 Quest 独立放置记录：均有 5 张，确认到就绪分别 **2,146／2,065 ms**，其中累计让步 **73.8／68.7 ms**；最慢的单次同步上传已达 **71.5／86.2 ms**。让步期间也可画加载界面。直接删延迟，无法消除最大的单次上传，还可能把几张图挤在一帧。WebGL 暂缓改上传节奏。
