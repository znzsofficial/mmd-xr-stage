## 预热触发与本机复核

舞台只在**手动放置一个新角色成功且物理关**时登记机会。下一舞台帧提交一个不设超时的 idle callback；回调再核对房间代次、在场角色、物理开关以及是否有交互／加载任务。没有空闲回调或浏览器不支持就等用户显式开启。导入、空场、物件、移动已有角色、失败／有警告的放置和自动恢复都不会登记。退场取消未运行的回调；已开始的模块请求只保留页级模块，不回写舞台。

`mmdRuntime/bulletModule.ts` 只加载物理入口和同版本 JS/WASM，不调用创建后端或世界。成功的 Promise 供同页后续开启复用；若显式开启撞上进行中的预热，先共用请求，预热失败才按显式请求重试一次。独立的预热失败不设物理错误、不后台循环重试。`physicsRebuilds[].work.moduleAtFirstRequest` 记录本次开关的第一个模型取模块时的状态：`cold`、`warming`、`warmed`、`warm-failed` 或 `demand-reuse`（源自显式开启）；再看同一操作的 `bulletModuleMs`。

**本机功能对照，非真机收益预测。** Edge 157.0.4341.60，Vite 本地服务，同一原版 505 骨 PMX、735180 字节身体 VMD、0.1×，真实 Bullet，不绘制／预上传；冷／预热各一张新页面，均绑动作并经过一帧，再等 2 秒后开→关→开。可用[切换探针](../../scripts/physics-toggle-probe.html)分别以 `?startup=cold`、`?startup=warm` 重跑。

| 桌面单次（ms） | 第一次开 | 其中模块 | 关 | 再开 |
|---|---:|---:|---:|---:|
| 按需，`cold` | 143.2 | 136.6 | 13.5 | 2.6 |
| 放置后空闲加载，`warmed` | 6.9 | 0.1 | 12.9 | 3.5 |

两页空载时 Bullet 资源请求均为零；显式开启前 runtime 都是零刚体／零 step。拦截真实模块的原生建世界入口，两页全程均只创建 2 次（两次显式开启），JS/WASM 各取一次。室内编排测试另验空场、失败、移动、切区、收回和回场不会误预热。桌面测量是 `setPhysicsEnabled()` 到返回的墙钟，不覆盖 XR 的 UI 发布、两眼渲染或模块预热期间的帧抖动。并行开发时不做 CPU 时间大扫频。

## 8815 ms 的回场：先辨认是不是同一瓶颈

真机一次成功泳池→教室：43 ms 入队前 + 8726 ms 队列到就绪 + 46 ms 到可见回调。队列中模型任务 1561 ms、身体动作 6207 ms；另有约 958 ms 未归入这两项。之前草坪→教室的身体动作仅 10 ms。不能由这些总量推断文件相同、同为命中，或 6.2 秒都在解析。

布局保留原 `File` 对象；跨房缓存属于观看会话而非单个房间。命中后只共享只读解析结果，仍需 `model.setAnimation()`。关物理的 PMX 通常走 WASM 动画适配器：绑定普通 VMD 时用源字节为当前模型创建 clip；与开物理时的 JS 求值器不同。保留同一模型的专属 clip 或整套 runtime 跨房不是安全的通用捷径。

[回场动作探针](../../scripts/room-motion-probe.html)加 `?physics=off`，同一本机角色和 VMD，四次均重建模型，比较无解析缓存／命中／命中／无解析缓存。实际走 `wasm-adapter`：不缓存两轮的读取及解析等待 23.2／19.6 ms，绑定 3.8／1.7 ms；命中两轮等待 0.0／0.1 ms，绑定 1.9／1.6 ms，动作任务总计 2.1／1.7 ms。四轮各取 65056 个骨矩阵／表情 Float32 值，哈希相同，无 Bullet 资源或世界。这个文件未复现 6.2 秒；维持最多 4 份、合计源字节 4 MiB 的界限。

**下次只需同一趟游玩导出。** 新页空场进入教室，手动放置同一角色、绑同一动作，先关物理播放，再开／关；在关物理时离开并返回教室。先比 `startup.firstVisibleXrFrameMs`、`placements[].confirmToReadyFrameMs` 和首次开的模块状态／忙段，观察放置后到开物理前有无新增顿挫。若自然使用时首开仍是 `cold`，也请保留这份报告。

回场看 `roomRestores[].motionWork[]`（每个实际执行的身体／表情任务一条，无文件名、路径或轨道名），按以下顺序定位：

- `cache` 为 `miss`／`oversize`／`none` 且 `loadWallMs` 长：检查相同 File 的会话生存期／逐出／超出预算；先拆读文件与解析再定缓存策略。`pending` 表示接的是未完成请求；`hit` 表示查找时解析结果已就绪。等待含调度，不能当成解析 CPU。
- `hit` 且 `setAnimationMs` 长：针对记录的 `evaluator`（`wasm-adapter`／`js`／`other`）在本机复测该适配器的绑定，核对不同角色、不同动作及释放时机，再决定如何减少重复转换。
- 两项都短而 `taskWallMs.body` 仍长：查任务内其余同步操作、恢复姿态、合并动作、失败回滚与主线程调度。两项都已包含在动作任务墙钟内，不再相加到回场总耗时。
