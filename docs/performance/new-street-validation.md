# 校园环线与秦淮河街：浏览器实走记录

2026-11-21 · 共用开发版舞台，桌面 Edge / SwiftShader、IWER Quest 3 输入。只用本地生成的橙色三角 GLB。以下记录的是功能和画面，不是头显帧率或舒适度测量。

## 普通 XR 移动与摆放

- **草坪 → 电玩厅 → 泳池 → 电玩厅 → 草坪**：从草坪原入口走过印刷铺，到涂鸦门；从外梯底部上到 3.4 m 平台，绕东侧廊桥下到计时台，原路上坡、下楼、回到草坪。四道门均由左摇杆穿过。草坪实放 `(36, 0, 3.65)`、电玩厅转角实放 `(-7.84, 2.05, -24.55)`、计时台实放 `(5.55, 0, -20.22)`。印刷铺座椅、裁判椅、池水都显示拒放预览；扳机松开后没有生成物件。
- **喜院 → 秦淮 → 喜院**：从喜院入口步行到桥冠，在 `(-17, 0.42, 10.90)` 实放；沿灯门去歌楼正码头，再在 `(11.60, 0, 8.10)` 摆放并走回喜院入口。桥下河水、码头外水面和茶案都拒放。草稿未确认时持续压杆不能穿门；取消草稿后，同一次持续压杆能过门。
- 两次实走都从偏心的头显跟踪位置 `(0.19, 1.57, -0.14)` 开始，右杆实际转 30°，以偏离门轴的视线穿门。六次跨门保留朝向和视图代次；校准后的眼高没有在门边跳变。回访草坪、电玩厅和喜院时，标记物在新网格实例上恢复了原位置和朝向。证据中的位置均为房间世界坐标，按 **X, Y, Z** 排列。
- **闭环另走一遍**：草坪 → 电玩厅 → 计时台后，沿原泳池东岸穿旧门回草坪，一直走回原点附近；没有借菜单重置位置，也没有卡在最后一道门。

## 屏幕输入

六个方向都通过屏幕机位菜单切景。实测鼠标从背包选取标记，点击前先检查像素确实属于画布：印刷铺前、电玩廊桥中段 `(-22.30,1.08,-24.43)`、计时台、喜院桥冠和歌楼码头可放；印刷铺座椅、裁判椅、池水和两岸河水拒放。回访后，新建的电玩廊桥、草坪及桥冠标记均保留原位置和朝向。若提示条盖住靠近脚边的目标，可先取消草稿，后退再点。

在喜院，滚轮将相机从 `x=-21.90` 拉到 `-27.22`，经过门线再拖拽环绕，仍留在原场景。按 F 升到 `y=3.03` 后，持续按 S 平移至 `x=-23.82`，也没有误入秦淮。

站立高度另测一次真实键盘往返：按住 S 从喜院退入秦淮，门后继续移动 **1.17 m**；松开后停住。按住 W 回喜院，门后继续 **1.68 m**；实际 keyup 后再次停住。两方向均未在门边重置方向或高度，回桥后眼高随坡面正常上升。该检查覆盖了切景销毁旧相机控制器时误清已按键的修复。

## 画面与复验入口

初验截图发现草坪借景前院的侧缝及电玩廊桥下露出天色。修后的印刷街实拍可见连续草地；廊桥远望可辨堤岸、滤池、泵房和树带。秦淮门内外均能同时看到脚下石路、灯门和茶铺；跨门后的傍晚色调、船和歌楼属于秦淮场景。检查了逐镜头 WebGL 程序的顶点／片元 `COMPILE_STATUS` 和 `LINK_STATUS`，泳池另确认实际水面程序参加绘制。

本机复验脚本在 `%TEMP%/opencode/xr-browser-smoke/`；从项目根目录运行。每次输出独立的 `new-street-evidence/<模式>-<路线>-<时间>/report.json`，包含姿态、鼠标像素或 XR 扳机事件、拒放预览、回访变换及截图。

```powershell
$qa = "$env:TEMP/opencode/xr-browser-smoke"
node "$qa/local-vite-run.mjs" dev "$qa/new-street-matrix.cjs" 'xr:campus,xr:river,xr:loop' 'screen:campus,screen:river'
```
